# 수령 지갑 교체 및 무결성 보완 — 운영 반영 체크리스트

이 문서는 배포 승인이나 운영 DB 변경 기록이 아니다. 구현/격리 DB 검증과 운영 확인을 구분한다.
`main` 머지는 Railway 배포를 시작하므로 아래 확인 없이 머지하지 않는다.

## 변경 범위

- 구·신 지갑 이중 서명으로 수령 지갑만 교체. 기존 wallet/NFT/payout 이력 보존, 부모 재발급 없음.
- 이후 보상금은 새 대표 지갑, 완료 NFT는 기존 부모 NFT 지갑으로 발급.
- 에이전트 주소/키 비교를 정규 계정·키 바이트 기준으로 통일. 서명용 `0x`/`inj1` 주소는 보존.
  새 검증 키는 base64로 저장하고, 기존 hex 키도 같은 정규 식별자로 비교한다. 기존 API 키는 회수하지 않는다.
- 에이전트 verify/rotate/revoke는 사용자 → agent 순서로 잠금. 동시 탈퇴 뒤에는 USER_NOT_FOUND.
- 최초 지갑 challenge 발급/검증도 사용자 → challenge → wallet 순서로 잠근다.
  교체와 같은 대상 지갑을 동시에 검증해도 유니크 인덱스를 서로 점유하며 교착하지 않는다. 잠금 대기 후 만료도 다시 검사한다.
- 0028은 검증된 agent 계정/키의 소유자를 `agent_identity_reservation`에 보존한다(RLS on).
  REVOKED여도 다른 소유자의 등록/활성화를 DB에서 거부하며, 구버전이 이해하는 409 매핑을 유지한다.
  유니크 인덱스 대기 **전·후** 모두 검사한다. 신버전 verify도 키 정리/발급 전에 예약을 재확인한다.
- NFT 마지막 성공 기록 실패가 이미 완료된 ATTACHED를 되돌리지 않는다. 기존 FAILED 복구도 attached_at을 보존.
- NFT 조회는 typed CW-721 TokenInfo/NftInfo 미존재만 false. 통신 404·계약 미존재·잘못된 owner_of 응답은 오류로 유지.
- 새 교체 API(`WALLET_REPLACEMENT_ENABLED`)만 기본 OFF. 정확한 소문자 문자열 `true`일 때만 동작한다.
- **기존 NFT 자동 발급은 유지한다.** `NFT_MINTING_ENABLED` 미설정/빈 값/`true`이면 기존 체인 설정으로 워커가 계속 처리한다.
  명시적 `false`로 중지하며, 다른 비어 있지 않은 잘못된 값도 안전하게 중지한다. 지갑 교체 활성화와는 독립이다.
- 0026은 교체한 사용자의 새 payout INSERT를 현재 대표 지갑으로 보정하고, 새 자식 NFT INSERT를 기존 부모 지갑에 고정한다.
  이전 바이너리의 오래된 조회 결과에도 적용된다. 과거 payout/NFT 행은 수정하지 않는다.
- 0027 이후 ID를 생략한 새 NFT는 부모=user_id, 자식=submission_id 기준 UUIDv5다.
  기존 랜덤 ID 및 명시적으로 복원하는 ID는 변경하지 않는다. ID는 비밀/인증 토큰이 아니다.

## 1. 운영 데이터 사전 점검 (운영 DB 접근 권한자)

기존 운영 스크립트와 같은 DB 접속 환경으로 실행한다. 이 명령은 `BEGIN READ ONLY`와 SELECT만 사용하고,
0025 적용 전에도 실행할 수 있다. 출력은 충돌 agent/user ID이며 키·서명·이메일은 출력하지 않는다.

```sh
node scripts/check-agent-identities.js
```

- 종료 0: 감지된 충돌/잘못된 주소 없음. 이 결과는 실제 대상 DB에서 실행한 결과여야 한다.
- 종료 1: 중복 활성 계정/키, 타인이 검증한 예약과 충돌한 활성 행, 모든 행이 REVOKED여도 검증 소유자가 여러 명인 예약,
  해석 불가 주소 또는 키↔주소 불일치. **배포 중단**.
  오래된 미검증 EVM 키도 ID/검증 여부로 보고한다. 검증된 키 불일치와 구분해서 조사하며 자동 수정하지 않는다.
- 종료 2: 잘못된 옵션/설정. `--yes`, 자동 정리 옵션은 없다.

충돌을 자동 합치거나 검증된 소유자를 선택하지 않는다. 운영자가 소유 증명과 제출·지급·NFT 이력을 확인하고,
승인·감사를 남기는 이력 보존형 정리 절차를 별도 결정해야 한다. 단순 삭제/주소 덮어쓰기/키 강제 회수로 우회하지 않는다.

## 2. 배포 전

1. DB 백업 및 복구 절차 확인. 인덱스 교체는 쓰기를 잠시 대기시킬 수 있으므로 데이터 양과 반영 시간대를 검토한다.
2. 0024(교체 challenge/RLS), 0025(순수 정규화 함수·인덱스), 0026(구버전 writer 보호), 0027(신규 NFT 식별자),
   0028(검증 agent 소유자 예약) 적용 순서 확인. 0025/0028이 충돌을 발견하면 해당 파일 전체를 롤백한다.
   0028은 agent 쓰기 잠금 아래 사전 검사·예약 백필·트리거를 함께 설치하므로 중간 상태로 쓰기를 허용하지 않는다.
   기존 행·서명 주소·소유자·인덱스를 임의로 덮어쓰지 않는다. 앞서 성공한 마이그레이션 파일은 남으므로 실패 원인을 해결 후 재시도한다.
   마이그레이션/SchemaGuard를 끄거나 충돌 검사를 지워 배포하지 않는다.
   정규화 함수는 public RPC가 아니므로 PUBLIC 실행 권한을 회수한다. 기본 DB 소유자 접속은 그대로 동작한다.
   별도 비소유자 BE 역할을 쓰는 환경은 정규화 함수와 `stable_nft_issuance_id(text,uuid)` 실행 권한을 역할에 한정해 확인한다.
   `agent_identity_reservation` SELECT/INSERT 권한과 RLS 정책도 해당 BE 역할에 한정해 확인한다(기본은 migration/BE 동일 소유자).
   트리거는 SECURITY INVOKER이며 기존 BE 쓰기 권한이 필요하다. public RPC나 SECURITY DEFINER 우회는 추가하지 않는다.
3. 운영 계약의 **기존 토큰 owner_of 성공 응답**과 **명확히 없는 토큰의 CW-721 storage 오류**를 읽기 전용으로 확인한다.
   SDK의 protobuf data bytes에 JSON owner가 있어야 한다. 계약이 다른 오류 형식을 쓰면 먼저 fixture/판정 지원을 추가하고 검증한다.
   네트워크 404를 토큰 미존재로 다시 완화하면 안 된다. 이 확인에는 민팅·송금이 필요하지 않다.
4. 이 릴리스에 네트워크/컨트랙트 전환을 섞지 않는다. 기존 잡은 현재 환경설정을 사용하므로 전환은 runbook §8의
   미완료 NFT job 0개 사전 검사와 별도 승인으로 진행한다. DB unique만으로 다른 체인의 재발급을 막지는 못한다.
5. API 계약 산출물 `npm run contract:export`가 변경 코드와 일치하는지 확인하고 FE 담당자에게 교체 계약을 전달한다.

## 3. 승인된 배포 이후 (이 문서 작성만으로 수행되지 않음)

- **1단계: 지갑 교체 OFF로 호환 버전 배포, 기존 NFT 발급은 유지.** 민팅 설정은 새로 추가할 필요 없다.
  이미 `NFT_MINTING_ENABLED=false`로 중지한 환경은 그 선택을 보존한다. 마이그레이션을 유지하고 모든 writer 버전을 확인한다.
  구버전 프로세스는 배포 시 실제 종료·드레인을 확인한다. 새 환경 플래그를 모르므로 변수 변경만으로 중지됐다고 판단하지 않는다.
  최초 지갑 연결의 잠금 순서도 바뀌므로 구·신 지갑 writer를 오래 혼재시키지 않는다. 무오류 전환이 필요하면
  지갑 challenge/verify 쓰기만 짧게 제한한 뒤 구버전 요청을 드레인한다. NFT 자동 발급을 일괄 중지할 필요는 없다.
  agent 예약 트리거가 설치되기 전 충돌 쓰기가 생겼으면 0028이 배포를 거부한다. 사전 점검 결과를 재사용하지 말고 충돌 원인을 확인한다.
- **2단계: 기존 NFT 발급 정상 흐름과 큐/체인 조회 응답 확인.** 일반 배포에 민팅 중지/수동 재개를 강제하지 않는다.
  DB 복원·체인 전환·보안 사고에는 별도로 `NFT_MINTING_ENABLED=false`를 명시하고 모든 워커를 중지·드레인한다.
- **3단계: 구버전 writer 드레인·지급/NFT 호환 검증 후 `WALLET_REPLACEMENT_ENABLED=true`.** 환경값은 운영자 승인 표시일 뿐,
  모든 서버가 새 버전이라는 자동 증거가 아니다. 플래그를 끄면 새 challenge/verify 모두 503 `WALLET_CHANGE_DISABLED`.
- 마이그레이션 적용 및 `/health` 확인. health는 체인 민팅 성공 증거가 아니다.
- 기존 로그인/기존 agent API 키/서명 검증/지급 요청의 읽기·정상 흐름 확인.
- NFT PENDING/PROCESSING/FAILED 및 INVALID_NFT_OWNER_RESPONSE 증가 감시. 원인 확인 전 무조건 재큐잉하지 않는다.
- FE에서 응답 유실을 실패 확정으로 표시하지 않고 동일 verify 또는 `/auth/me`로 결과 확인하는지 점검.
- 실제 확장 지갑·testnet 민팅·중복 token ID 거부는 별도 승인된 체인 검증으로 남긴다.

## 4. 롤백·복원 경계

- 교체 첫 성공부터 `user.receiving_wallet_revision`이 남는다. challenge 정리/기능 OFF로 지우지 않는다.
  이후 앱 롤백 시에도 0024–0028 스키마/트리거/인덱스·소유자 예약은 유지한다. down migration/옛 wallet 주소 덮어쓰기는 하지 않는다.
- 승인할 롤백 최저 버전은 이 릴리스의 사용자→agent 잠금, 별도 owner/wallet 조회, 부모 지갑 고정,
  worker pause·claim fencing·보수적 체인 판정을 보존해야 한다. 0026은 옛 INSERT 둘의 호환 보호일 뿐 임의 구버전 전체를 안전하게 만들지 않는다.
- **DB 복원 전 두 플래그 OFF → 모든 old/new API·워커 중지/드레인 → 이미 전송된 tx 확정 확인 → 복원 → 체인 대조 → 호환 앱 재기동**.
  pause는 이미 브로드캐스트된 tx를 취소하지 않는다. 같은 프로세스의 느린 조회 뒤에도 전송 직전 플래그를 재확인하며,
  pause로 미실행한 자기 잡은 retry_count 증가 없이 반환한다. 이미 보낸 mint의 결과는 pause 후에도 기록한다.
- 새 결정론적 NFT는 같은 user/submission ID와 같은 계약에서 NFT 행/잡이 유실돼 다시 등록되어도 같은 token ID로 조회·복구한다.
  **기존 랜덤 NFT, 복원 범위 밖에 생성됐던 user/submission, 다른 체인/계약, 명시적 새 ID 입력에는 이 보장이 없다.**
  미설정/빈 값/`true`인 환경은 자동 발급이 유지되므로 복원을 자동 감지해 멈추지 않는다. 복원 전 명시적 `false`가 필요하다.
  과거 발급과 체인 tx를 대조해 원래 ID/소유/잡을 복원한 후 재개한다.
  기존 랜덤 ID를 새 결정론적 ID로 바꿔 재발급하지 않는다.

## 보존하는 정책 / 이 릴리스가 하지 않는 일

- 부모 NFT는 user_id당 1개다. 지갑 주소당 평생 1개 또는 실제 사람당 1개 정책으로 바꾸지 않는다.
- 분실·해킹 지갑 강제 복구, NFT 이전, 관리자 임의 지갑 교체를 추가하지 않는다.
- ATTACHED는 현재 표준 CW-721 경로의 DB 관계 상태다. 온체인 Nestable 연결을 주장하지 않는다.
- 같은 이름의 기존 인덱스로 이전 서버도 유니크 충돌을 기존 409로 처리하지만, 이것만으로 이전 서버 전체의 안전성을 보장하지 않는다.
- 탈퇴는 이미 등록된 NFT 작업 취소가 아니다. 탈퇴 시 미민팅 작업을 취소할지는 별도 정책 결정이며 이번 변경에서 바꾸지 않는다.
